# Form 5472 / Pro Forma 1120 Generator — Phase 0 Discovery Audit

Prepared per `docs/TASK-5472-generator-fixes.md` §4, as amended by §10. No code changed. No database queried. All examples are synthetic.

## 1. Stack

- **Language/framework:** TypeScript, Next.js 14.2.35 (App Router — route groups `src/app/(app)`, `src/app/(marketing)`, plus `src/app/admin`, `src/app/api`). React 18, Zod 4 for validation, react-hook-form for wizard forms.
- **Database:** PostgreSQL via Prisma 6.19 (`prisma/schema.prisma`), datasource comment and `PlaidConnection` note both point at Neon. Decimal columns (`@db.Decimal(15,2)`) hold money; `taxYears Int[]` is a Postgres array.
- **PDF production:** entirely in-process with **pdf-lib 1.17.1** — no pdftk/qpdf/poppler, no separate rendering service. This matters directly for amendment 1: the stack cannot run native PDF binaries in production (Vercel), only in dev/CI.
- **Object storage:** Cloudflare R2 via `@aws-sdk/client-s3` (fields are commented "R2 key" throughout `prisma/schema.prisma`, e.g. `generatedPdfKey`, `signedPdfKey`, `dissolutionCertKey`).
- **Payments:** Stripe (`src/app/api/checkout`, `src/app/api/stripe-webhook`).
- **Bank data:** Plaid (`plaid` SDK, `src/app/api/plaid`) plus manual CSV/XLSX upload (`papaparse`, `xlsx`) parsed in `src/lib/bank/parsers.ts`.
- **Fax:** Telnyx (`src/app/api/telnyx-webhook`, `src/app/api/fax`, `ReceivedFax` model).
- **Auth:** hand-rolled HMAC session tokens for customers (`src/lib/session.ts`), admins (`src/lib/admin/auth.ts`, `src/lib/admin/identity.ts`) and partners (`src/lib/partner/auth.ts`) — all `crypto.createHmac`/`timingSafeEqual`. A `.clerk/` directory exists at the repo root but `@clerk/nextjs` is **not** in `package.json` dependencies; it appears vestigial, not the live auth path.
- **Tests:** Vitest 4 (`npm test` → `vitest run`).
- Two unrelated products share this repo: `hktax/` (a separate Hong Kong salaries-tax app) and this Form 5472 product. `src/lib/wizard/{mapping.ts,schemas.ts,wizardState.ts}` and `src/lib/tax/*` are leftover Hong Kong tax code (types like `PAPersonInput`, MPF calculations) with **zero importers** under `src/app` or `src/components`; `mapping.ts` even imports `@/lib/tax/params`, which doesn't exist in this repo, so it wouldn't compile if ever wired in. These are dead code, not part of the Form 5472 questionnaire. The real field-level schemas live in `src/lib/schemas.ts`.

## 2. The generator

- **Entry point:** `generatePackage(f: Filing): Promise<GeneratedPackage>` in `src/lib/pdf/generatePackage.ts:1060`. Callers: `src/app/api/checkout/route.ts` (first generation after payment), `src/app/api/generate-pdf/route.ts` (customer-triggered regeneration, gated to `PAID`/`PDF_GENERATED` status only — later statuses 409), `src/app/api/stripe-webhook/route.ts` (webhook-driven generation), and `src/lib/admin/filingActions.ts` case `"regeneratePdf"` (line 507) for reviewer-triggered regeneration.
- **Blank IRS PDFs:** `public/forms/f1120--2024.pdf`, `public/forms/f1120--2025.pdf`, `public/forms/f5472.pdf` (loaded via `loadBlank()`, `generatePackage.ts:196`, from `public/forms/`).
- **Field addressing:** AcroForm field names (XFA-style paths like `topmostSubform[0].Page1[0].f1_9[0]`), defined in `src/lib/pdf/fieldMaps.ts` for `form5472FieldMap`, `form1120_2024FieldMap`, `form1120_2025FieldMap`. `setText`/`check` in `src/lib/pdf/fillForm.ts` look the field up by name and **silently log-and-skip** if it's missing or the wrong type (`fillForm.ts:6-26`) — a field-map typo produces an incomplete PDF, not a build error.
- **Filling functions:** `fillForm5472()` (`generatePackage.ts:201`), `fillForm1120()` (`generatePackage.ts:321`), `buildSupportingStatement()` (Part V, freehand-drawn PDF, `generatePackage.ts:409`), `buildCoverLetter()` (`generatePackage.ts:662`), `buildReasonableCause()` (`generatePackage.ts:808`).
- **Flattening:** `flatten(form)` in `fillForm.ts:79-85` calls pdf-lib's `form.flatten()` inside a `try/catch` that only `console.warn`s on failure — **a failed flatten is swallowed, not surfaced**. Each of the two form PDFs (1120, 5472) is flattened individually right after it's filled, **before** being merged into the output document (`generatePackage.ts:308, 385`), which is the correct order per amendment 1's replacement pipeline (fill → appearances → `form.flatten()` → assert no widgets). The "assert zero widgets remain" half of that instruction is not implemented anywhere.
- **Merging:** `copyAll(dest, src)` (`generatePackage.ts:1203-1206`) uses `dest.copyPages(src, src.getPageIndices())`. Assembly order in `generatePackage()`: cover letter → (if any year is late) **one** reasonable-cause statement → then, per tax year in `f.taxYears`: Form 1120 → Form 5472 → Part V supporting statement. There is no Part VI step anywhere in the file (confirmed by a full-file search for `PartVI`/`partVI` — zero matches outside a `1k_partsVIII` comment).
- **Callers of `generatePackage`:** `src/app/api/checkout/route.ts`, `src/app/api/stripe-webhook/route.ts`, `src/app/api/generate-pdf/route.ts`, `src/lib/admin/filingActions.ts`. No cron job calls it.

## 3. Authored documents

None of the three authored documents (cover letter, Part V statement, reasonable-cause statement) use an external template file — they are built by direct pdf-lib `drawText` calls inside `generatePackage.ts` (functions named above). There is no `config/filing_package` module or equivalent anywhere in the repo (confirmed: no file matches `config*filing*` and no import of any such module).

**Current Re line and enclosure wording** (`generatePackage.ts:705, 783`):
```
Re: Form 5472 + Pro Forma Form 1120 for {llcName}
...
Enclosed please find Form 5472 with attached pro forma Form 1120 for the above
foreign-owned U.S. disregarded entity, for the tax year(s) listed.
```
Neither matches the required config phrase `"pro forma Form 1120 with Form 5472 attached"`, and the body sentence is literally the **reversed** phrase that A22 says must never appear.

**Current timeliness wording** (`generatePackage.ts:739-758`, verbatim conditionals): *"These filings are being submitted under the Delinquent International Information Return Submission Procedures (DIIRSP)."*, *"This package also includes a timely filed return for tax year(s) …"*, *"These are timely filed for the tax year(s) indicated."* Spec 5.7 requires **no** sentence about timeliness/lateness/compliance in the cover letter; the current letter is built almost entirely around exactly that sentence.

**Signature headings:** RCS uses `"Signed under penalties of perjury:"` (`generatePackage.ts:980`, hardcoded literal — happens to match the currently-desired value but isn't centralised). The cover letter instead uses a plain `"Signed:"` (`generatePackage.ts:799`) — the two authored documents disagree with each other today.

## 5. Bank imports (amendment 6)

Files: `src/lib/bank/parsers.ts` (CSV/XLSX → `ParsedTransaction[]`), `src/lib/bank/categorize.ts` (classification), `src/components/wizard/TransactionsReview.tsx` (review UI), `src/components/wizard/PlaidConnectButton.tsx` (Plaid path), `src/app/api/plaid/exchange/route.ts`, `src/app/api/filings/[id]/statements/route.ts`.

1. `detectProvider()` (`parsers.ts:6-18`) sniffs the CSV header row for Mercury / Wise / Relay / Brex; each has its own row-mapper producing `{ date, description, counterparty, amountCents }` (amounts parsed with `toCents()`, `parsers.ts:20-27`, dates normalised to `YYYY-MM-DD` with `isoDate()`, `parsers.ts:30-34`). Plaid transactions presumably feed the same `ParsedTransaction` shape (`PlaidConnectButton.tsx` imports `CategorizedTransaction`/`Category` directly from `categorize.ts`).
2. `categorize(tx, owner)` (`categorize.ts:78-124`) applies ordered rules: internal transfer (regex heuristics for Mercury sub-account moves) → **owner-named counterparty → `contribution` (inflow) or `distribution` (outflow) — the only two categories that reach Part V** → known card-issuer outflow → known payment-processor inflow → default outflow to `vendor_expense` / inflow to `unknown`.
3. `TransactionsReview.tsx` lets the customer override any row's category, then computes `reportableTransactions: y.transactions.filter(tx => REPORTABLE.includes(tx.category))` where `REPORTABLE = ["contribution", "distribution"]` (`TransactionsReview.tsx:23, 493`) — this filtered array is what gets PATCHed as `FilingYearData.reportableTransactions`.
4. The dollar totals sent alongside it (`contributions`, `distributions`) are computed **client-side** by summing `amountCents` and dividing by 100 (`TransactionsReview.tsx:284, 352, 429`) — plain floating-point dollars, no cents-then-round-half-up step.
5. Server-side, `src/app/api/filings/[id]/route.ts:501-616` **trusts the client-submitted `contributions`/`distributions` numbers** (Zod-validated only for type/range via `makeYearDataSchema`, `schemas.ts:357-365`) and writes them straight to `FilingYearData`. It never recomputes them from `reportableTransactions`, so the aggregate totals and the itemised rows can drift out of sync (a client bug, a partial edit, or a tampered payload would not be caught). `generatePackage.ts:1143` then reads `line1f = yd.contributions + yd.distributions` directly — Form 5472 lines 1f/1h are ultimately whatever the browser sent, not a value derived from the Part V rows at generation time.
6. `Q-01`/`Q-02`'s owner-paid-formation-costs framing exists only as a hint paragraph in the "final return"/formation-year UI (`TransactionsReview.tsx:617, 665-666`, "If you paid the state filing fee, registered agent, or funded the bank account…") rather than as discrete, individually-dated line items per category — verify in Phase 1 whether this becomes one lump "contribution" row or several.

## 6. Filing-status logic

Almost entirely centralised in **`src/lib/schemas.ts`** (lines 180-342), consumed by `src/lib/completeness.ts` (checkout/admin "is this payable" gate) and `generatePackage.ts`:

- `filingDueDateUtc()` / `rawFilingDueDateUtc()` (`schemas.ts:203-221`): 15th of the 4th month after year-end, or after the dissolution month for a short final year. Weekend roll implemented (`rollWeekendToMonday`, `schemas.ts:227-232`) — **federal holidays are deliberately not rolled** (documented rationale at `schemas.ts:191-202`: the omission can only make the tool call a still-timely return late, judged the safer failure direction).
- `isYearDelinquent()`, `isExtensionValid()`, `effectiveDueDateUtc()`, `extensionUnclear()` (`schemas.ts:249-342`) implement the full Form-7004 gate: a 7004 is valid only if transmitted on/before the original due date; "not sure" defers the year's classification entirely (never asserted late or timely); the extension answer is scoped to `max(taxYears)` only. Manually checked against T5/T6 in the task file (dissolved 14 Jul 2026 → due 15 Nov 2026, a Sunday → correctly rolls to 16 Nov 2026; with a valid extension → 15 May 2027, a Saturday → correctly rolls to 17 May 2027) — **this arithmetic is already correct.**
- Inputs stored: `extensionFiled`, `extensionTransmittedAt`, `extensionMethod`, `extensionDestination`, `extensionProofKey` on `Filing` (`prisma/schema.prisma:234-238`) — raw customer answers persisted, not just a derived flag.
- `src/lib/completeness.ts` (`requiresReasonableCause()`, `extensionAnswerRequired()`, `filingCompletionIssues()`) deliberately recomputes live rather than trusting the stored `Filing.isDiirsp` snapshot, explicitly to avoid the documented 2026-08-25 incident.
- **No injectable clock** anywhere: every date computation calls `new Date()`/`Date.now()` directly. There is a test file `src/lib/schemas.extension.test.ts`, but nothing in `schemas.ts`/`completeness.ts`/`generatePackage.ts` exposes a seam for tests to fix "today".
- **Gap:** `FilingWizard.tsx:340` still shows the "Reasonable cause" wizard step only `if (filing.isDiirsp)` — the same stale snapshot `completeness.ts` was rewritten specifically to stop trusting. A filing whose live status has turned late after `isDiirsp` was last written could reach `requiresReasonableCause() === true` (blocking checkout per `completeness.ts`) while the step that lets the customer type the narrative is hidden.

## 7. Tax-year handling

Selectable years: `Array.from({ length: maxYear - 2017 }, (_, i) => 2018 + i)` (`FilingWizard.tsx:1279`), where `maxYear = isFinalReturn ? currentYear : lastCompletedTaxYear` (`FilingWizard.tsx:1230, 1278`, mirrored server-side in `maxSelectableTaxYear()`, `schemas.ts:91-94`, which re-reads the clock on every call rather than closing over a module constant). The **upper** bound is correctly dynamic and clock-driven; the **lower** bound is a hardcoded `2018`, not "the formation year" as spec's Q-14 literally asks for.

Period start/end: `periodStartFor()`/`periodEndFor()` (`generatePackage.ts:141-181`) return `01/01`/`12/31` unless the formation/dissolution date falls inside the year being rendered, in which case they return the actual formation/dissolution `MM/DD` — both read in UTC deliberately, with an explicit comment about the west-of-UTC slippage bug. **These feed Form 5472's header fields correctly** (`fillForm5472`, `generatePackage.ts:222-225`). **They do not feed Form 1120's header at all** — see §10, G-04.

## 8. Reviewer tooling

Admin can both edit and regenerate. `src/lib/admin/filingActions.ts` exposes a `runFilingAction()` dispatcher (line 241) with, among others, `"updateField"` (line 613 — whitelisted fields including `llcBusinessCode`, all address fields, `reasonableCauseNarrative`, and the four extension fields, each write logged to `FilingChangeLog` with `adminId`/`source`/`beforeJson`/`afterJson`/`reason`/`changedAt`) and `"regeneratePdf"` (line 507). Because `updateField` writes straight to the same `Filing`/`FilingYearData` rows `generatePackage()` reads, an admin correction automatically "survives" a subsequent regeneration — there is no separate override layer to reconcile. `src/app/api/generate-pdf/route.ts:22-28` already refuses to regenerate a filing whose status is past `PDF_GENERATED` (`SIGNATURE_PENDING`/`SIGNED_UPLOADED`/`FAXED`/`CONFIRMED` → 409), which is consistent with ground rule 3 (never touch a signed/faxed package). Routes: `src/app/admin/filings/[id]/page.tsx` + `EditFieldsCard.tsx` (UI), `src/lib/admin/filingActions.ts` (mutations), `src/app/api/admin/v1/filings/[id]/route.ts` (read API).
